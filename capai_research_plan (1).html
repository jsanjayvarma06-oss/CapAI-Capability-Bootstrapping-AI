What we've built, precisely. CapAI is a self-expanding capability acquisition system — an orchestration layer that detects when a task exceeds its current function library, autonomously diagnoses the gap (DiagnosticAgent), generates sandboxed Python code via an LLM (CodeWriter), verifies it across three independent layers — known tests, history replay, self-generated edge cases — (TestingAgent), and promotes it through a gating ManagerAgent into a persistent, deduplicated registry. It also implements a tiered cross-agent capability sharing protocol with independent re-verification on the receiving side (TrustedImporter). This is a real, non-trivial agentic systems prototype and a valid research artifact in its own right.
Pick one research angle — these are our publishable gaps
Angle A — Empirical evaluation of 3-layer verification
Best pick
Our TestingAgent has three layers: known tests, history replay, and self-generated edge cases. Nobody has empirically measured what each layer actually contributes — does Layer 3 catch bugs Layers 1+2 miss? How often does the loop converge within 1 vs 3 attempts? Clear experimental design, no competing prior work.
Angle B — Cross-agent capability sharing trust model
Strong pick
sharing.py implements a tiered trust model with re-verification on import. Build a controlled experiment: export capabilities with planted bugs, import via TrustedImporter, measure detection rate. A concrete security result for agentic systems that no prior work addresses.
Angle C — Registry deduplication analysis
Narrower fit
ManagerAgent uses SequenceMatcher (threshold 0.85) for near-duplicate detection. Measure false-merge and false-non-merge rates at varying thresholds across a benchmark capability set. Proposes embedding-based similarity as an improvement.
Angle D — Sandbox escape surface
Niche but sharp
sandbox.py runs LLM-generated code in a subprocess without restricting network access, filesystem writes, or resource exhaustion. Systematically characterise what an adversarially-crafted capability can do. A security/safety paper on autonomous code execution boundaries.

Position the work & choose our angle
Weeks 1–2
▾
Week 1 Read 5 papers that define your context
  • Voyager (arXiv 2305.16291) — the closest prior system to CapAI. An LLM-driven agent that iteratively acquires JavaScript skills in a Minecraft environment. Their verification is single-layer (execution success only) — not three-layer like ours. Read Section 3 in full; their skill library has no registry lifecycle or deduplication.
  • CodeAct (arXiv 2402.01030) — LLM agents that generate and execute code as actions. Widely cited but focuses on task completion, not persistent capability accumulation with a registry lifecycle.
  • ToolBench / ToolLLM (arXiv 2307.16789) — large-scale tool learning for LLMs. Their tools are pre-defined; CapAI synthesises new ones on demand. Note the difference carefully in our related work.
  • Self-expansion literature — search "LLM capability self-expansion 2024 2025" on Semantic Scholar. Confirm that registry-managed, three-layer-verified, cross-agent-shareable capability acquisition has not been formally evaluated as a system.
  • SWE-Bench (arXiv 2310.06770) — the standard benchmark for LLM code generation. Useful for contextualising CapAI's code generation quality claims, even though CapAI's domain is narrower.
  • After reading, write a half-page "what exists vs. what CapAI adds" memo. This becomes the core of your Introduction and Related Work sections.

Week 2 Confirm our angle & design the experiment
  • Pick Angle A or B (or both if our team has 3 people). Decide as a team before Week 3 — the experimental design is completely different for each.
  • If Angle A (3-layer verification): design a benchmark of 30–50 capability tasks spanning trivial (celsius conversion), moderate (fibonacci, palindrome check), tricky (string manipulation with edge cases), and domain-specific (statistical functions). Write ground-truth test suites for each.
  • If Angle B (sharing trust): design a set of 20–30 capabilities with planted bugs of known types — off-by-one, missing type check, wrong formula, silent wrong output for edge input. Export via CapabilityExchange, import via TrustedImporter, measure detection rate by bug type and layer.
  • Pre-register our experimental design on OSF.io before running any experiments. We have a working system, so pre-registration is feasible and signals methodological rigor to reviewers.
Angle chosen. Benchmark or bug suite designed. OSF pre-registration posted. We know what our Table 1 will look like before we run a single experiment.

Instrument the system & run experiments
Weeks 3–6
▾
Week 3 Add logging & metrics — instrument before we measure Critical
  • Add structured event logging to the Orchestrator's _emit() calls so every acquisition attempt produces a machine-readable JSON lines record capturing: task name, attempt number, each layer's pass/fail, final outcome, LLM call count, wall-clock time per stage.
  • For Angle A: add per-layer bug-catching attribution to testing_agent.py — when a capability fails, record which layer first caught it. This is our main measurement.
  • For Angle B: instrument TrustedImporter.import_from() to record which verification layer catches each planted bug.
  • Add a deterministic test mode: when CAPAI_TEST_MODE=1 is set, bypass LLM calls and use the heuristic fallback — lets you run hundreds of trials cheaply before spending API credits.
Python logging / jsonlines pytest fixtures
Weeks 4–5 Run the main experiments
  • Angle A run: for each of our 30–50 benchmark tasks, run CapAI 3 times with different random seeds. Record: did it succeed? How many attempts? Which layer caught each failure? What was the false-positive rate per layer?
  • Angle B run: for each of our 20–30 planted-bug capabilities, run the full import-and-verify pipeline. Record: was the bug caught? Which layer? Did the bug type affect detection rate?
  • Run in deterministic/heuristic mode first (free, instant) to confirm our logging pipeline is correct, then run with LLM enabled for real results. Budget ~$5–20 in API credits for Groq or Anthropic.
  • Save all raw logs — we will need full provenance to answer reviewer questions about reproducibility.
pytest Groq API (free tier) pandas (log analysis)
Week 6 Ablation study — the layer contribution analysis
  • Re-run experiments with one layer disabled at a time: (a) no history replay, (b) no self-generated edge cases, (c) only known tests. This ablation directly answers "what does each layer add?" and is our strongest empirical result.
  • For Angle A: report "unique bug detection rate" per layer — bugs caught by Layer N that Layers 1 to N-1 missed. This table is our paper's central finding.
  • For Angle B: compare detection rate with re-verification vs. trust-on-import (no re-verification). The gap between those two numbers is the concrete security value of our trust model.
  • Also compute: overall acquisition success rate, mean attempts to success, mean wall-clock time per acquisition, LLM call count per acquisition. These populate our evaluation table.
Full experiment results + ablation complete. Main result tables and figures ready. We know our headline numbers.
3
Analysis, figures & secondary contributions
Weeks 7–8
▾
Week 7 Comparative baseline & qualitative analysis Strengthens the paper significantly
  • Build a baseline for comparison: implement a "single-shot" version of CapAI — no acquisition loop, no verification, just generate-and-execute once. Compare success rate against the full CapAI loop. This baseline comparison is what turns our paper from a system description into an empirical evaluation.
  • Qualitative analysis: pick 5 interesting cases where CapAI failed or took 3 attempts. Write them up as case studies — what went wrong, which layer caught it, how the code changed between attempts. These make the paper readable beyond the numbers.
  • Build our 3 main figures: (1) layer-contribution bar chart (unique detection rate per layer), (2) attempts-to-success distribution histogram, (3) capability taxonomy breakdown (trivial / moderate / tricky) by success rate.
Week 8 Known limitations & proposed extensions
  • The sandbox restricts execution to JSON-serializable inputs/outputs — document this as a deliberate design constraint, not merely a limitation, and argue why it is the right tradeoff for autonomous capability generation.
  • SequenceMatcher-based deduplication uses Levenshtein-style surface similarity — discuss why embedding-based similarity would be a better long-term approach and sketch what that extension would look like.
  • The git-based MCP server versioning is local-only — discuss how adding a remote push step enables distributed capability provenance tracking across multiple CapAI instances.
  • Self-generated edge cases skip negative numbers deliberately (see code comment in testing_agent.py). Argue both sides and propose a more principled edge-case generation strategy as future work.
Three figures done. Baseline comparison complete. Case studies written. Limitations section drafted. Full story assembled.

Writing & submission
Weeks 9–12
▾
Weeks 9–10 Write the paper
  • Use ACL or NeurIPS LaTeX template on Overleaf. For a systems paper, IEEE double-column is also appropriate depending on our target venue.
  • Write in this order: Section 3 (System Design) → Section 4 (Evaluation) → Section 2 (Related Work) → Section 1 (Introduction) → Abstract.
  • Key framing for the intro: "We present CapAI, a self-expanding capability acquisition system, and the first empirical evaluation of multi-layer automated verification for autonomously-generated code capabilities. We show that [Layer 3 catches X% of bugs missed by Layers 1–2], and that cross-agent capability sharing with independent re-verification catches Y% of bugs undetected at the exporting instance."
  • The System Design section should reference actual class names — Orchestrator, ManagerAgent, TestingAgent, TrustedImporter — and specific design decisions (why subprocess isolation, why JSON-only sandbox).
  • Release CapAI as open source on GitHub and reference it in the paper. Systems papers with a public codebase are taken more seriously at review.
